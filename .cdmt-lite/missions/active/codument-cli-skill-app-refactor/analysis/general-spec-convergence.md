## 3. 从 cdmt-lite 真正应借鉴的东西

精简的核心不是删检查，而是减少不承重的流程，把控制器围绕期望态与实际态组织起来：

1. 用户意图和已确认行为约束决定“要达成什么”；工作图与技术路线是“怎么尝试达成”的假设。
2. 当前证据决定下一动作；不因为上一步进入某阶段，就照着固定事件表往下走。
3. 尚未看清的问题保留为未知，必要时先选择能减少不确定性的观察；不提前拆成看似确定的任务。
4. 一次行动包含证伪它的验证，尽早发现错误理解或未接通的边界；终态再回原始目标独立重观察。
5. 每次失败先判断它否定了什么，改变被否定的前提或动作；完整审计不替代日常反馈，也不逐节点重复。

“计划是假说”不是可以删除已批准的困难要求。即便约束最早由 AI 提出，一旦被有权者确认，就要按相应决策/变更入口修订；实现失败不授权缩小目标。

## 4. 建议的通用主干：意图—观察—行动的收敛关系

### 4.1 拟单是持续理解，不是一次性补全所有规格

Agent 先从简短意图、仓库现状和已确认选择形成当前理解：什么变化算有价值、哪些约束已经成立、什么还不确定。记录在现有 proposal/design/findings，不引入新 schema 或每项必填表。

能查证的先查证；普通且后果可逆的选择用保守默认并标明假设。影响范围、数据、兼容性、成本或核心体验且没有安全默认的歧义才请求用户决策。可逆性要看现实后果和返工成本，不能只看代码能否 git revert。

不要把没有说清的事项直接声明成“范围外”，也不要以模糊目标为由自行扩成完整大型产品。确认足以决定当前切片的语义即可；后续观察可以继续细化，但不得暗中增加或取消承诺。

### 4.2 下一步优先解决最危险的理解或连接假设

选择下一动作时问：哪一个安全、成本合适的观察，最可能揭示当前方案为何不能达成承诺？

可能是只读调查、特性冻结测试、隔离实验，也可能是获准实现后的最小连贯切片。不是每次都先建完整端到端系统，更不要求在生产环境制造真实副作用。实验需要实现时，必须落在用户授权的实施阶段与隔离边界内。

局部模块通过并不能推出目标通过。对实际承诺，追查合法消费入口、真实输入或操作序列、预期结果及适用不变量是否接通。验收形态由项目决定，而不是固定为 API/UI/某一种浏览器。

### 4.3 验证阶梯是遗漏检查，不是充分正确性证明

复用现有 Exists → Substantive → Wired，不再加一套同义清单。但沿入口到结果跑通只证明一个观察面，还需由承诺推导相应边界、状态变化、重复/失序、时间尺度、资源生命周期或负向性质；没有这些承诺时不强加。

举例仅用于证明可泛化，不形成产品分类：

- 游戏：真实输入能否引起预期游戏状态与玩家可见结果；动画接通不证明命中判定或体验正确。主观“好玩/紧张”无法由测试替用户裁决，可用小原型和用户反馈校准。
- 基础库：公开发布/导入入口是否满足声明的行为、兼容性和资源性质；内部函数通过不证明消费方能用，并发与内存安全也不能由一个正常调用证明。
- 基础设施：在隔离或模拟边界下观察声明的配置生效、调和、恢复或幂等性质；产出备份对象不证明能恢复一致数据，不为真实性测试破坏生产数据。

性质测试、差分参考、故障注入、操作序列测试或人工体验观察都是可选测量方法，不是每个项目的强制全套。

### 4.4 独立验证要独立重建目标，而非仅换会话

fresh 仍是 verify、GapLoop、AttractorCheck 的既定协议，不能删除。但新会话若只读同一派生计划、运行同一偏窄测试，仍可能共享同一误解。

Reviewer 从原始意图、已确认取舍和适用吸引子重建目标，再看当前实现及不利证据；派生 Acceptance 是导航，不是覆盖上限。对于明确或已确认的承诺可判缺口；对模糊描述存在多种合理解释时，应记录未决与证据需求，不能把自己的偏好擅自升级为硬失败标准。

需要补什么观察取决于风险与已配置协议，不按四角色强制生成四 Agent。必须明确局部任务自验、最终目标重观察、显式 fresh 审计三者的适用范围；不能借“消除冲突”减少已配置 hook、轮数或 fresh 强度。

### 4.5 纠偏修被证伪的部分，不靠重试碰运气

失败后先判断：是目标解释不足、实现违反承诺、观察条件不成立，还是交付协议没闭合？这是分析问题，不是另建一个封闭错误分类系统。

修改对应 owner：实现错修实现；实际目标解释或计划假设错则受控 revise；工具/环境/收据协议问题由观测或交付基础设施修复。证据不足时不能擅自归为业务 PASS 或业务 FAIL，也不应自动触发生成应用修复。

复验必须解释新信息从何而来，并覆盖原 finding 与受影响范围；必要回归和配置检查保持。当前无新观察/无条件变化时不原样重试。失效证据撤回效力并链接替代证据，不删除旧收据、抹掉失败或重置轮数。

## 5. 如果使用通用吸引子，应约束关系而非列场景

建议先归并已有方法与吸引子，不急于再增加长文档。若最终确有独立共享吸引子的必要，它只维护少数稳定关系：

1. 完成声称只覆盖有充分观察支持的已确认承诺；局部任务/测试成功不能代替缺失的目标面。
2. 计划和观测是目标的派生物；调整实现路线或修复测试，不得未经授权反向改写目标。
3. 行动依据当前差距与证据，反馈改变下一动作；没有新依据的重复与删除失败证据不属于合法收敛。

相应排除集：未接通的能力被声明完成、同一误解生成的自洽代码/测试替代目标验证、为 PASS 缩小目标、把观测失败当业务修复触发、无变化重复运行。

这些是拟议判据，不是已经创建或注册的 attractor。具体运行方法仍由 workflow/operation 单一 owner 维护，不能在吸引子复制整套操作步骤。

## 6. 最小改造顺序（建议，尚未授权实施）

1. 先消除已有规范中的技术分类主干及独立性适用冲突，明确上述通用关系；原实例可保留为非封闭示例。不动用户需求文本，不再叠加另一套覆盖表。
2. 在现有 plan-track/plan-mission 的目标推导处加强“当前理解/关键未知/最小可信观察”；在现有任务与调度机制表达，不增加强制的探针 Track、阶段或控制器框架。
3. impl-track/impl-quick/impl-mission 以实际目标和承诺边界选择行动及证据；verify/gap-loop 从原始依据重建目标，保持既有角色分离和配置 hook。
4. 借现有 findings/report/receipt 表达前提、覆盖范围、失效及替代关系；CLI 只做已有结构/路径/运行合同的机器检查，不尝试确定性判断任意业务语义。
5. 再验证方法效果：先用历史 finding 做协议反例/无模型检查，后续获授权时保持需求、模型、预算与 harness 固定作对照，并加入跨领域样本检验泛化。无模型协议检查只能证明规范/基础设施性质，不能报告成真实编码成功率。

成本优化仍以按需读取 source closure、前提有效的确定性证据复用、受影响范围验证和 event wait 为手段。不得复用 fresh 语义 verdict，不删 gap-loop/hook/attractor 能力，也不把“小切片”包装成隐式降低最终验收强度。
